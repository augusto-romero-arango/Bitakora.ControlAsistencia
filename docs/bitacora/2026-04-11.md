El hito del dia. El gate mecanico quedo integrado al pipeline TDD despues del reviewer y antes de crear el PR:

```
Stage 1 (test-writer) → Stage 2 (implementer) → Stage 3 (reviewer) → Sync main → Stage 4 (coverage gate) → PR
```

Mide cobertura de lineas por archivo, los clasifica en "logica" (umbral 95%+) o "excluido" (boilerplate sin valor de test unitario), remedia automaticamente con el test-writer si hay gaps (maximo 1 iteracion), e incluye tabla de cobertura en el cuerpo del PR. Nunca bloquea — los gaps se reportan, no se imponen. ADR-0018 documenta el diseño completo.

## Problemas encontrados

**El profiler dinamico de dotnet-coverage no funciona con .NET 10 en macOS ARM64**
El problema habia pasado desapercibido: el profiler corre sin errores pero produce datos incorrectos o vacios. La unica forma de obtener cobertura real es instrumentacion estatica (`dotnet-coverage instrument` antes de `collect`). El CI probablemente llevaba tiempo produciendo reportes vacios por este mismo motivo — se verificara en el proximo PR que toque cobertura.

**Las clases autogeneradas inflaban el denominador artificialmente**
`DirectFunctionExecutor`, `WorkerExtensionStartupCodeExecutor` y otras clases que el SDK de Azure Functions genera en tiempo de compilacion aparecian en el reporte de cobertura. ControlHoras pasaba de ~85% real a 54.5% reportado. El fix: excluir esos assemblies del ReportGenerator con la whitelist del issue #52, y ademas excluir el codigo generado del XML de cobertura con `--exclude-attributes` en la instrumentacion estatica.

**Pipeline TDD fallido en issue #57 — el test-writer en modo patch no puede ponerse en rojo**
El pipeline TDD para testear el `FunctionEndpoint` del ServiceBus trigger en ControlHoras fallo en Stage 1: todos los tests pasaron (exit code 0) en lugar de fallar. El problema estructural: el test-writer en "modo patch" (la implementacion ya existe, hay que agregar tests para codigo existente) no tiene mecanismo para escribir tests que fallen — la implementacion ya esta ahi y los tests pasan de entrada. El pipeline TDD asume fase roja antes de fase verde; cuando no hay fase roja, el gate de Stage 1 rechaza el trabajo.

Esto genero el issue #67 (refactor para extraer `ServiceBusEndpointBase`) que se implemento manualmente en lugar de via pipeline. La pregunta abierta del planner quedo registrada en la field note: *"evaluar si el gate post-patch debe ser 'tests pasan' en vez de 'tests fallan'"*.

**Nombres de workflows de smoke tests colisionaban en GitHub (08:37)**
Dos workflows distintos tenian el mismo `name:` en GitHub Actions, lo que causaba que uno sobreescribiera al otro en la UI. Fix simple: diferenciar nombres. El commit `7b8d146` lo corrigio sin issue asociado.

## Lo que descartamos

**Opcion A del coverage gate: el reviewer absorbe la medicion**
El reviewer ya puede agregar tests. Agregarle instrumentacion y analisis de cobertura lo convertiria en el detector del mismo tipo de fallo que el podria producir. Ademas, su contexto ya es denso — agregar mas responsabilidades degrada todo. Descartada por falta de separacion de responsabilidades.

**Opcion C del coverage gate: cobertura como contexto informativo**
Pasar los datos al reviewer sin gate ni remediacion. Descartada porque los LLMs tienden a reportar "cobertura aceptable" sin actuar cuando ya tienen mucho contexto. El juicio del LLM reviewer no es mecanismo confiable para decidir si un gap importa.

**Excluir assemblies de terceros uno a uno en dotnet-coverage.settings.xml**
El approach de blacklist no escala: cada nueva dependencia requiere un nuevo patron de exclusion. La solucion correcta es whitelist en ReportGenerator.

**coverlet como alternativa a dotnet-coverage**
Tiene problemas similares con .NET 10 y xUnit v3 MTP. No se considero seriamente — ya tenemos experiencia con dotnet-coverage y el problema era de uso (profiler vs. instrumentacion estatica), no de herramienta.

**Branch coverage (por ahora)**
La instrumentacion estatica en .NET 10 no reporta datos de branches (`branch-rate="1"` siempre). Se usa line coverage como proxy. ADR-0018 documenta la limitacion y la condicion para revisar: cuando dotnet-coverage soporte branch coverage con instrumentacion estatica, ajustar umbrales.

**Perseguir los 2-3% faltantes en FranjaOrdinaria y SubFranja**
Son paths de serializacion/igualdad que no representan riesgo de negocio. Incluirlos en el gate agregaria ruido sin detectar gaps reales.

## Aprendizajes

1. **Un profiler que falla silenciosamente es mas peligroso que uno que falla con error.** dotnet-coverage en modo dinamico corre sin quejarse en .NET 10/macOS ARM64 pero los datos son inutiles. El sintoma era cobertura anormalmente baja o reportes vacios — no un error claro. La solucion es siempre instrumentacion estatica en .NET 10.

2. **La cobertura como detector de brechas requiere medir lo correcto.** Con las clases autogeneradas en el denominador, el 54.5% reportado era practicamente ruido. Antes de preocuparse por umbrales, hay que asegurarse de que el denominador sea solo codigo propio. Basura entra, basura sale.

3. **El pipeline TDD tiene un caso ciego: no sabe operar sobre codigo existente.** El ciclo rojo-verde-refactor asume que no hay implementacion al inicio. En modo "patch" (agregar tests a codigo ya escrito), Stage 1 nunca falla porque la implementacion ya esta. Este es el limite del pipeline — lo que esta mas alla requiere intervencion humana o un modo de operacion diferente.

4. **Un gate mecanico con clasificacion explicita elimina la discusion sobre metricas de vanidad.** No es "90% de cobertura global" — es "este `CommandHandler` especifico, en este PR, tiene 87% de cobertura de lineas y el umbral es 95%". La especificidad hace el gate accionable y elimina la ambiguedad de lo que se mide y lo que no.

5. **Disenar y desplegar en el mismo amanecer es posible cuando el diseno es claro.** Las sesiones del planner de las 05:59 y 06:39 produjeron el diseno del gate con tres alternativas evaluadas. A las 08:12, PR #61 estaba mergeado. El diseno claro (incluyendo lo descartado) fue el acelerador — no habia ambiguedad en la implementacion.
