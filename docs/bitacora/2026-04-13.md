**El descubrimiento de la tarde: smoke tests con verde y dead letters acumulándose (field note 19:02)**
La sesión de planner de las 19:02 partió de una observación concreta: después de correr los smoke tests, la suscripción `smoke-tests` terminaba con mensajes en dead letter que nadie había consumido. Los tests pasaban — pero el sistema quedaba contaminado.

El diagnóstico fue preciso: los tests HTTP de `SolicitarProgramacionTurno` verificaban solo el status code (202 o 409) y no los eventos publicados al Service Bus. La convención del smoke-test-writer de separar en dos archivos (`{Comando}SmokeTests.cs` para HTTP, `{Comando}SbSmokeTests.cs` para SB) era la causa raíz estructural: la clase HTTP no se sentía responsable de los eventos que su función publicaba.

El diseño resultante fue el **patrón purge-before-act**: `PurgeAsync` (ReceiveMessageAsync + CompleteMessageAsync en loop) antes de cada Act para limpiar basura histórica, ejecución secuencial obligatoria con `DisableParallelization` para que un test no drene el mensaje del siguiente, y **fail-on-mismatch** si un mensaje llega y no matchea el predicado — fallo explícito con diagnóstico, no abandon silencioso. La regla de dominio quedó clara: dead letters en `smoke-tests` significan que algo está roto, no que la suscripción acumula basura.

## Problemas encontrados

**Race condition en `--permission-mode bypassPermissions` bajo concurrencia**
El flag oficial de Claude CLI para ejecución no-interactiva no es confiable cuando múltiples instancias corren en paralelo. El problema no es accionable desde el proyecto — es un bug (o comportamiento no especificado) del CLI. La mitigación vía allows explícitos en `settings.json` funciona, pero es más frágil: requiere enumerar paths adelantados. Queda la pregunta abierta de si es un bug conocido de Claude CLI o un comportamiento esperado bajo concurrencia.

**`WaitForMessageAsync` en ControlHoras era código muerto**
El fixture de ControlHoras tenía el método implementado pero ningún test lo invocaba. Se descubrió al revisar la alineación con el patrón purge-before-act. No era un bug activo, pero confirmó que la separación HTTP/SB había dejado los fixtures de Service Bus a medio implementar en ese dominio.

**Workflow de smoke tests con JSON de matriz mal formateado**
Al implementar el purge-before-act en el issue #93, el workflow de GitHub Actions fallaba porque el JSON de la matriz de tests no estaba compactado. Fix: agregar `jq -c` al paso de generación del JSON. Commit `908b4f3`, sin issue asociado.

## Lo que descartamos

**Drenado dentro de `WaitForMessageAsync`**
Hacer el drenado de mensajes residuales dentro del método de espera tiene un problema de timing: podría consumir el mensaje del test actual antes de que el predicado lo evalúe. Descartado.

**Suscripciones efímeras por test**
Crear y destruir una suscripción por cada ejecución de test garantizaría aislamiento total, pero es overengineering para un entorno dev con bajo throughput. La suscripción compartida con purge explícito es suficiente. Descartado.

**Paralelismo en smoke tests de Service Bus**
Los smoke tests contra Service Bus requieren ejecución secuencial para que el patrón de purga funcione. Paralelizarlos complicaría el drenado sin aportar beneficio real en dev. Descartado con `DisableParallelization`.

**Investigar el bug de concurrencia de Claude CLI**
No es accionable desde el proyecto — el código de Claude CLI no está bajo nuestro control. Documentado como limitación conocida y mitigado con allows explícitos.

## Aprendizajes

1. **Un test que no verifica todos los efectos secundarios de su función miente.** El smoke test de `SolicitarProgramacionTurno` reportaba verde porque su función (el HTTP trigger) respondía 202. Pero la función también publicaba eventos que iban a dead letter. El test medía correctamente lo que medía; el problema era que medía demasiado poco. La regla "una clase por comando, todos los efectos secundarios" cierra esa brecha estructuralmente.

2. **La separación de responsabilidades entre archivos puede crear zonas de nadie.** La convención HTTP/SB en dos clases partía el contrato de una función entre dos archivos. Cada archivo se sentía responsable de "su" parte — ninguno se sentía responsable del conjunto. Cuando las responsabilidades se distribuyen así, los gaps aparecen justamente en las fronteras.

3. **El patrón purge-before-act requiere ejecución secuencial como invariante.** No es una restricción accidental — es parte del diseño. Sin `DisableParallelization`, el drenado de un test puede consumir el mensaje esperado por el siguiente. La secuencialidad no es una penalización de rendimiento: es el mecanismo que hace que el patrón sea correcto.

4. **Las herramientas que fallan silenciosamente bajo condiciones de concurrencia son las más peligrosas.** El race condition de `--permission-mode bypassPermissions` era invisible en ejecución secuencial — solo aparecía cuando dos pipelines corrían en paralelo. El síntoma era "el pipeline falló por permisos", no "hay un race condition en el CLI". Sin la field note del post-mortem de las 04:54, habría sido fácil diagnosticar mal.

5. **Crear y cerrar un issue en 16 minutos es posible cuando el problema está completamente entendido antes de implementar.** El issue #84 existió 16 minutos. No fue velocidad imprudente — fue que el diagnóstico ya estaba completo en la field note antes de crear el issue. La creación del issue fue el último paso del análisis, no el primero.
