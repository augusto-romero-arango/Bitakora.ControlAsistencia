# 2026-09-03 - Encontrar primero, programar después

> Para pedir programación desde un asistente necesitábamos una búsqueda de personas con identidad inequívoca; mientras la diseñábamos apareció un bug del binding MCP que deformaba fechas y GUIDs antes de llegar a las tools.

## Lo que se logró

**Dimos al asistente una ruta desde la búsqueda hasta la solicitud.** El usuario precisó el flujo: encontrar personas en Consultas y pedir en Comandos una programación para una lista de identificaciones completas, con sede explícita y una ventana de hasta 31 días. El código de colaborador no es único y el nombre de sede tampoco; por eso la tool resuelve por dentro la identificación, el nombre de turno (sí único) y el código de sede, sin confiar en que el agente reconstruya claves. La solicitud no es un lote atómico: el MCP hace N POST individuales, con paralelismo acotado y mejor esfuerzo, e informa programados, conteo de omitidos y fallidos con motivo. No inventamos un aggregate de lote para una orquestación de herramientas.

**La búsqueda ganó una vista propia, no un QUERY de fichas sobrecargado.** #587 materializó `DirectorioColaborador` con tokens de nombre y número normalizado; #590 añadió `QUERY colaboradores/directorio` y la configuración de lectura del documento; #588 publicó `buscar_colaboradores` con la forma de respuesta de `listar_colaboradores` pero semántica de palabras completas. Detectamos que el Id de la vista ya era la identificación completa (`CC-79879078`): otro campo e índice para el mismo dato eran redundantes. El número se limpia como `Identificacion.Crear` (puntos, guiones y espacios), y el nombre se tokeniza separando caracteres no alfanuméricos; para la contención de todos los tokens dejamos como salida probada `MatchesSql` con `@>` si LINQ/GIN no traduce. PRs #593, #595 y #596 llevaron la cadena al código.

**Restauramos argumentos string antes del binding de la extensión MCP.** Después de #574, `registrar_colaborador` fallaba con una fecha válida; `listar_colaboradores` y `consultar_programacion` tenían el mismo defecto latente. Verificamos en el worker MCP 1.6.0 que el converter transforma strings con forma de fecha o GUID en objetos `DateTimeOffset`/`Guid`, y que el binding posterior a `string` no los convierte. #586/PR #591 introdujo un middleware por servidor que toma el JSON crudo del `BindingData` y repone las hojas string en `ToolInvocationContext` antes de bindear; mantuvo el comportamiento fail-open si falta el dato. Se añadió una llamada smoke válida a `consultar_programacion`, antes cubierta solo por error o ausencia de fecha.

**Completamos la costura de despliegue de `solicitar_programacion_turno`.** #589/PR #597 resolvió terna, turno y sede; solo acepta coincidencia exacta de cada identificación pedida, de modo que un número sin tipo queda omitido en vez de programar a otra persona. El smoke siembra sede y colaborador mediante tools y turno por HTTP, y espera el directorio sin disparar POST para omitidos. #592/PR #594 añadió la suite smoke de Comandos al grupo `smoke-tests-dev`: esta tool sí cruza el bus, a diferencia de las altas iniciales. Quedó documentada la nomenclatura «Directorio de colaboradores», «Sede de programación» y la ventana de trabajo en el glosario.

## Problemas encontrados

**Los smoke tests anteriores escondían un defecto de producción.** `consultar_programacion` no ejercía su camino feliz con fechas; la extensión MCP alteraba el valor antes de que un helper en la tool pudiera leerlo. La solución requirió ir un nivel antes, al middleware de Functions. El comentario de tests que decía que `ToolInvocationContext` no era instanciable estaba obsoleto. No se abrió un issue upstream nuevo por decisión del experto.

**Un solo issue de directorio habría mezclado demasiados ejes.** Al contrastar #587 con el código encontramos, además, un `take` que el endpoint hermano clampea a [1,200] y una respuesta plana (no 422 ni envoltura). Dividimos vista/proyección (#587) y QUERY/smoke (#590), actualizando las dependencias de #588 y #589. Los pines de catálogo y smoke de Consultas todavía listaban cinco tools; #588 también debía corregir el README, desfasado desde #530.

## Lo que descartamos

- Helpers por tool sobre `context.Arguments`, downgrade de la extensión o cambiar parámetros string a `DateTimeOffset`: el texto original ya no estaba ahí y también se dañaban GUIDs; el middleware conserva el contrato de las tools (#586).
- Agregar al QUERY de fichas filtros de nombre y documento, crear una ruta `/busqueda`, aceptar solo prefijos o typos, o filtrar el directorio por ventana: mezclaban lentes de consulta y no seguían el vocabulario del recurso (MEF-ADR-0043).
- Un tope arbitrario de 50 colaboradores, fechas individuales `fechas[]`, sede por defecto desde la ficha o validar todo antes del primer POST: la ventana es marco de control, no mandato de atomicidad. La lista viaja como texto separado por comas por el contrato de parámetros MCP observado.
- Pedir la terna al agente o admitir un número de documento ambiguo como clave para programar: conservar la identificación completa evita persistir la identidad equivocada.

## Aprendizajes

1. **Una búsqueda para personas concretas y un listado para grupos son lentes distintos.** La vista nueva permite cambiar reglas léxicas sin alterar `FichaColaborador` ni su QUERY.
2. **Una prueba de error no sustituye un camino feliz para detectar coerción del transporte.** El converter de MCP 1.6.0 transformaba fechas que parecían perfectamente válidas, y el bug cruzaba ambos servidores (evidencia: #586/PR #591).
3. **La vista y su proyección pueden entregarse antes del endpoint sin ser código huérfano.** El worker ya produce el documento; el lector lo consume en el siguiente issue. El corte respeta el límite entre ReadModels/Projections y Function App.
