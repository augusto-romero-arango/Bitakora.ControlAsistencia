## Contexto
El borrador #587 (nacido en la sesion 2026-09-03 06:34, MCP para solicitar programacion) traia vista, proyeccion, indices, QUERY y smoke en un solo issue. Se refino a listo verificando cada afirmacion contra el codigo y aplicando la revision de complejidad.

## Descubrimientos
- `ComputarStreamId(id) => id.ToString()` = `"CC-79879078"`: el `Id` de la vista YA ES la identificacion completa. El campo `Identificacion` del borrador era redundante (mismo criterio que la ficha) y su indice btree sobraba: el filtro por identificacion completa va sobre la PK.
- `Identificacion.Crear` limpia el numero a `[A-Z0-9]` (quita puntos/guiones/espacios). `NormalizarNumeroDocumento` de la vista debe calcar esa regla -- con trim+upper, "79.879.078" dictado al asistente no encontraria `79879078`.
- `Etiqueta.Normalizar` (privado, DomainEvents) colapsa la enie; la tokenizacion de nombres hereda esa consecuencia (Munoz = Muñoz), deseable para buscar.
- `ListarFichasColaborador` clampea `take` a [1,200] (smoke lo fija) y responde lista plana sin envoltura: el borrador contradecia al hermano en ambos puntos (422 y "envoltura").
- La traduccion LINQ de "todos los tokens contenidos" sobre un array de strings NO esta verificada para GIN; el fallback ya probado en #373 es un solo `MatchesSql` con containment `@>` del array completo (contiene-todos en una operacion).

## Decisiones
- Partir en dos, replicando el precedente #356 -> #373: #587 = `DirectorioColaborador` + `DirectorioColaboradorProjection` + registro Async + 3 indices (`NumeroDocumento` btree, `TokensNombre` gin, `NombreCompleto` btree) + unit tests + config-test del worker; solo toca ReadModels/Projections. #590 = `ListarDirectorioColaboradores` (`QUERY colaboradores/directorio`) + `Schema.For<DirectorioColaborador>().UseNumericRevisions(true)` en el Function App + config-test write-side + unit tests del endpoint + smoke; depende de #587 (`bloqueado`).
- Razon del corte: el issue unico disparaba 5 alertas (3 modificados, 4 familias de test, 3 tipos de artefacto, 2 ejes, >30 min). Sin huerfanos: la vista y sus estaticas las consume la proyeccion en el mismo PR; la tabla materializada sin lector no es codigo muerto (el worker la produce en dev desde el primer despliegue).
- El registro write-side (`UseNumericRevisions`) se mueve a #590 porque solo hace falta cuando el Function App lee el documento (incidente #294).
- Las estaticas `TokenizarNombre`/`NormalizarNumeroDocumento` viven en la vista (ReadModels): unico ensamblado que ven el worker (escribe) y el Function App (lee); misma razon que `CentinelaVigenciaAbierta`. Duplicacion deliberada de reglas de DomainEvents por islas (Rule of Three, 2a aparicion).
- Respuesta de #590 nombra `identificacion` (= Id) en el vocabulario de quien busca; sin `tokensNombre`.
- #588 y #589 pasan a depender de #590 (el endpoint), no de #587.

## Descartado
- Campo `Identificacion` separado del `Id` (redundante, verificado).
- 422 para `take` fuera de rango y envoltura paginada (simetria con el hermano).
- Un solo issue vista + QUERY.

## Preguntas abiertas

- Filtro por tokens en LINQ o `MatchesSql`: lo decide el EXPLAIN en #590.
- Sigue pendiente de la sesion anterior: declarar "Depende de #586" en #589 (smoke con fechas validas).

## Continuacion: refinar #588 (buscar_colaboradores, MCP Consultas)

### Descubrimientos
- Los unit tests de `Mcp.Consultas.Tests` viven PLANOS en la raiz (`{Tool}ToolTests.cs`) con `Fixtures/*.json` y `Soporte/`; el borrador los ubicaba en subcarpeta por tool.

- Los pines del catalogo (`...ExponeLasCincoTools...` nivel 2, `...MaterializaLasCincoTools...` smoke) enumeran 5 nombres con `BeEquivalentTo`: cualquier tool nueva los rompe si no se tocan (MEF-ADR-0048 s.6).
- `FiltroDeNombre` (cliente, subcadena, `IgnoreNonSpace`) es el filtro de `listar_turnos`/`listar_sedes` bajo el parametro `filtro_nombre`; la busqueda del directorio es por palabras completas en el servidor.
- La suite smoke de Consultas solo dispone de `mcp_extension` (OIDC runtime): no puede sembrar datos en Colaboradores.

### Decisiones
- Parametro `nombre` (no `filtro_nombre`): semantica distinta (palabras completas vs subcadena), nombre distinto para que el agente no asuma que "berm" funciona.
- Respuesta con los MISMOS campos que `listar_colaboradores` (`identificacion`, `nombre`, `codigoColaborador`, `codigoSede`, `vigenteDesde`, `vigenteHasta`); se descarta el texto `vigencia` y los alias `codigo`/`sede` del borrador. Record propio `ColaboradorEncontrado` (no reusar `ColaboradorFicha`: acoplaria contratos entre tools). Se omiten `tipoDocumento`/`numeroDocumento`/`tokensNombre` (relevancia).
- `take` upstream siempre 200 (colisiones de numero entre tipos pueden devolver mas filas que identificaciones); >200 identificaciones lo rechaza el endpoint y viaja como `RechazoDelDominio`.
- Smoke: tool call con `nombre: "test"` afirmando forma; para que `test` sea token real se ajusto #587: `TokenizarNombre` separa por todo caracter no alfanumerico ("[TEST] Smoke" -> [test, smoke]; "Garcia-Marquez" -> [garcia, marquez]).
- CA-6 corrige el drift del README (6 tools) en el mismo archivo que el issue ya toca.
- #588 no depende de #586 (sin fechas ni GUIDs).
- Labels: tipo:feature + dom:colaboradores + estado:listo + bloqueado (por #590).

### Referencias

## Continuacion: refinar #589 (solicitar_programacion_turno, MCP Comandos) + #592

### Descubrimientos
