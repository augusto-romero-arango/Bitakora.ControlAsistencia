## Contexto
Mefisto 0.15.0 (`Cosmos.EventDriven` 2.1.0, issues Mefisto #312/#313, ADR-0024 del marco decision #8)
introdujo un segundo camino de consumo para eventos privados intra-BC: consumirlos directo con
`IPrivateEventHandlerAsync<TEvent>` en vez de traducirlos a un comando espejo. Se pidio crear un
issue de refactor en el repo consumidor para adoptar el patron donde aplique.

## Descubrimientos
- El repo tiene un solo consumidor que califica: `AdicionarMarcacionCuandoMarcacionRegistradaCommandHandler`
  (dominio ControlHoras). Hoy implementa `ICommandHandlerAsync<MarcacionRegistrada>` con el parametro
  llamado `command` que en realidad es el evento; no existe tipo comando espejo -> caso degenerado del
  comando espejo (el evento ES el comando). Califica.
- `MarcacionRegistrada` es `IPrivateEvent` intra-BC y se rutea **in-process** via WolverinePrivateEventSender:
  no hay ServiceBusTrigger ni FunctionEndpoint para ella. Por eso probablemente NO hace falta
  `PrivateEventEndpointBase` (ese aplica a eventos que llegan por trigger). Se dejo como verificacion del pipeline.
- Quedan 2 command handlers legitimos tras la migracion (`RegistrarMarcacion` HTTP, `AsignarTurno`
  publico->comando), asi que `AgregarWolverineCommandRouter()` debe permanecer; ambos routers conviven.
- `PrivateEventHandlerAsyncTest<T>` comparte `CommandHandlerTestBase` con `CommandHandlerAsyncTest<T>`,
  asi que expone `PublicEventSender`: las aserciones de publicacion de `DiaCalculado` siguen funcionando.
- **Deriva de numeracion de ADRs**: hay tres esquemas distintos (docs/adr del consumidor, indice
  tematico de CLAUDE.md, y docs/adr del plugin 0.15.0). El indice de CLAUDE.md esta desincronizado
  respecto al plugin. Se cito cada ADR por tema + archivo del plugin + numero para evitar ambiguedad.

## Decisiones
- Se creo el issue **#209** "Consumir MarcacionRegistrada con IPrivateEventHandlerAsync en vez de
  ICommandHandlerAsync" como `tipo:refactor` + `dom:control-horas` + `estado:listo` + `bloqueado`.
- Bloqueado por **#207** (bump a Cosmos.Event* 2.1.0, OPEN); las abstracciones del patron no existen
  por debajo de 2.1.0.
- ADRs aplicables (numeracion del marco/plugin): ADR-0024 (doctrina, decision #8), ADR-0002 (DSL de test),
  ADR-0003 (cableado de routers Wolverine en Program.cs). NO aplican: serializacion (0012) ni naming de
  funciones Azure (0006).
- La decision de naming (`{Evento}EventHandler` + subcarpeta `EventHandler/` vs conservar el nombre
  descriptivo actual) se marco como decision revisable del pipeline, no como especificacion.

## Descartado
- 4 handlers/comandos revisados y excluidos con justificacion en el issue: `RegistrarMarcacion`,
  `CrearTurno`, `SolicitarProgramacionTurno` (comandos HTTP genuinos) y `AsignarTurnoCuando...`
  (consume `IPublicEvent` cross-BC; 2.1.0 no trae `IPublicEventHandlerAsync`).

## Preguntas abiertas
- ¿El routing in-process funciona con `IPrivateEventRouter` sin `PrivateEventEndpointBase`? (verificacion del pipeline)
- Decision final de naming de clase/carpeta: la juzga implementer/reviewer.
