## Contexto
El usuario llega con el trabajo de los ultimos 3 dias con el event-stormer (diseno del flujo RegistroDeMarcacion -> MarcacionRegistrada -> ControlDiario -> DiaCalculado) y pide un plan de implementacion.

## Descubrimientos
- El flujo completo tiene 4 cortes naturales, cada uno alineado con un comando/handler y sus eventos
- La cadena es estrictamente secuencial: cada issue modifica ControlDiarioAggregateRoot, impidiendo paralelismo
- La calculadora (discriminacion de horas por concepto) NO esta lista para issue — falta definir conceptos legislativos colombianos
- Los value objects legacy del catalogo (Turno, DiaOperativo, Marcacion) no existen como archivos — marcados como legacy

## Decisiones
- **HTTP como trigger inicial** para RegistrarMarcacion — Service Bus se hara en historias futuras
- **HoraCorteTraslapeNocturno hardcodeada a 4AM** pero como field explicito del aggregate, no quemada en la logica
- **4 issues como estado:borrador** — se refinaran en sesiones independientes antes de implementar
- **Sin issue para la calculadora** — requiere sesion de knowledge crunching previa sobre conceptos legislativos

## Descartado
- Crear los issues como estado:listo directamente (el usuario prefiere refinar por separado)
- Paralelismo entre issues (todos tocan el mismo aggregate)

## Preguntas abiertas
- Lista completa de conceptos de discriminacion segun legislacion colombiana (bloqueante para la calculadora)
- Como llegan las marcaciones por Service Bus (futuro)
- Recepcion de lotes de marcaciones
