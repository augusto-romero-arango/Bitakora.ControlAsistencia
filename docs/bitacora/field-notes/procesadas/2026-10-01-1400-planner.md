## Descubrimientos
- Canon (MEF-ADR-0031 seccion 3, enmienda 2026-09-12; plugin 0.40.1 instalado): 420 s por reloj, intervalo 5 s, tolerar HTTP transitorio, exito solo con el SHA exacto; al agotar, mensaje con SHA esperado + ultima respuesta + URL de `StartupLogs` de Kudu como diagnostico **manual** ("consultar Kudu activamente queda fuera de alcance: requiere OIDC, permisos y parsing de logs anexados"); sin fallo rapido; `/api/ready` conserva 120 s como presupuesto independiente.
- El canon admite dos materializaciones "deliberadamente distintas": gate en `Fixtures/ApiFixture.cs` (C#, dominio) y gate en bash dentro del reusable (MCP). Este repo usa la forma bash en **ambos** reusables: el de dominio desde HU-224 (`367bce8`, 2026-07-19), el MCP desde HU-516.
- Discrepancia estructural repo vs canon de dominio: `smoke-tests-dominio.yml` no pasa `Api__ExpectedSha` a `dotnet test` y las cuatro `ApiFixture.cs` (Colaboradores, ControlHoras, Programacion, Sedes) solo hacen `/api/health`. La nota de harness#1273 ("actualiza `Fixtures/ApiFixture.cs`") no aplica literalmente; la forma canonica aplicable es el bloque bash de `mcp-scaffolder` 0.37.14+. `WarmupFixture.cs` (ControlHoras) usa 120 s para el cold start del listener SB, no para el gate.
- El comentario del poll de `/api/ready` en `smoke-tests-dominio.yml` dice que "120s replica el mismo criterio de MEF-ADR-0031": el test del marco (`test-domain-scaffolder-version-gate.sh`) exige la redaccion contraria ("no comparte el timeout del gate por SHA"). Entra como CA-3.
- `tooling-pipeline.sh` 0.40.1 permite `tests/` (solo fixtures/helpers) y corre `dotnet build` si hay `.cs`; no hacia falta particion porque el alcance final es solo `.github/workflows/`.
- Estado colgado: `.mefisto/pipeline/pipeline-status-tooling-674.json` (harness 0.37.13, 2026-09-12) quedo en `running/setup`; el log muere al entrar a Stage 1, sin worktree, rama ni PR. Es estado local del usuario; no se toco.
