## Contexto
El product owner pidio "poner WorkOS y volver multitenant toda la solucion", con la condicion de que
Mefisto conservara las dos formas de trabajo (mono-tenant sin auth y multi-tenant con auth). El
reconocimiento revelo que el marco ya tenia la mitad construida: MEF-ADR-0028 (dos etapas de tenancy,
token declarativo -- la etapa (a) sigue siendo el default de greenfield, nada se elimina),
MEF-ADR-0032 (WorkOS+APIM con catalogo de trampas B1-B11) y los skills /install-workos, /install-apim,
/install-auth. El codigo del consumidor ya era tenant-aware por construccion (conjoined, CA-ADR-0027).

## Descubrimientos
- Vocabulario: **Tenant = empresa cliente = organizacion WorkOS**; actor **Administrador** (unico
  usuario autenticado); el **Colaborador NO se autentica**. Registrado en el glosario.
- Autenticacion mixta por diseno (MEF-ADR-0032): puerta APIM (JWT, anti-spoofing) + puerta directa
  (function key + headers declarados, para sistemas trusted). Quien porta la key puede actuar como
  cualquier tenant: la custodia de la key es el control.
- **ProxyTenantResolver (canon MEF-ADR-0028 etapa b) esta roto en el worker aislado**: decide su rama
  en el constructor con HttpContext null. Hotfix 66e7a80: identidad ambiente AsyncLocal +
  TenantContextMiddleware (ambos planos HTTP/ASB), patron ControlPlane. Reportado a Mefisto
  (harness#812); ADR local pendiente (#552).
- Ruta para MCP autenticado verificada en docs oficiales (2026-09-01): WorkOS AuthKit como
  authorization server MCP (CIMD, PRM) + validacion en la aplicacion (el soporte de plataforma de
  Azure esta en Preview y se descarta).
- Fragilidad de smoke: nombres fijos + limpieza al final => runs abortados dejan residuos y el
  siguiente run cae en cascada con 409 (#553).
- La purga de schemas exige reinicio inmediato de hosts (los objetos Wolverine/Marten se recrean
  solo al arrancar); el worker de proyecciones es Container App (ca-asist-dev), no Function App.

## Decisiones
- Camino minimo sin dominio de identidad: /install-apim directo (sin /install-auth) porque el
  onboarding de organizaciones es manual por dashboard y el adapter WorkOS no tendria consumidor.
- CORS: gateway instalado con placeholder localhost; el front SPA llegara despues. Claude via MCP
  es el front interino y sus usuarios se autentican con WorkOS.
- Dispositivos de marcacion: sistemas externos con M2M futuro asociado a tenant (#537, borrador).
  Hoy las marcaciones las cargan administradores autenticados.
- Datos de dev desechables: purga en el mismo despliegue del flip (doctrina MEF-ADR-0036).
- Flip ejecutado: PR #545 (gateway APIM, 30 add/0 destroy; migracion automatica de los 4 resolvers
  gracias al alineamiento previo #536).
- El gate empirico de claims (decodificar token real, MEF-ADR-0032 s.8) se pospuso por decision del
  usuario: revive como CA de #540 (sin token real del flujo MCP no se puede mapear tenant).

## Descartado
- Scaffold de dominio de identidad (sin caso de uso mientras el onboarding sea manual).
- EasyAuth/PRM de plataforma para el MCP (Preview + combinacion con OIDC custom no verificada).
- Perseguir los smoke rojos como bug del flip: era estado sucio en cascada (runs abortados con
  hosts caidos), no regresion.

## Preguntas abiertas

- Politica de APIM: verificar mapping claim->header con token real cuando exista (7b pospuesto).
