# 2026-09-02 - Dos MCP, un solo umbral OAuth

> Al sumar un servidor de comandos al MCP de consultas descubrimos que compartir el gateway no equivale a compartir el recurso protegido; además, un cambio de versión del scaffold movió el suelo bajo los issues recién planificados.

## Lo que se logró

**El MCP de Comandos pasó de idea a servidor desplegado.** Partimos de los contratos de `POST /api/sedes` y `POST /api/colaboradores`, que en ese momento devolvían 202 sin cuerpo. Acordamos pedir `fecha_inicio` explícita para el colaborador —una fecha histórica no puede convertirse silenciosamente en «hoy»—, no reingresar a quien recibe 409 y devolver un eco compacto con advertencia de visibilidad eventual, sin esperar a la proyección. La cadena #570 → #571 → #572 → #573 → #574 terminó con scaffold, APIM, derivación de `org_id`/`sub` y las tools `registrar_sede` y `registrar_colaborador` (PRs #577, #581, #583-#585). Las tools no se declararon idempotentes: repetir un código puede dar 409. Su smoke de escritura no entró en `smoke-tests-dev` porque estas dos altas no cruzan Service Bus.

**Reconstruimos el contrato de seguridad de dos recursos OAuth en un gateway compartido.** Consultas ya ocupaba el PRM del gateway; Comandos necesita otro Resource Indicator y otro `aud`. Contrastamos el PRM por recurso con ruta de RFC 9728 §3 y el soporte de múltiples Resource Indicators de WorkOS. La versión 0.35.0 de Mefisto traía un layout mejor: una API PRM compartida con una operación por path, así que #575 reconcilió `apim-mcp-api` con la interfaz del scaffold sin perder las correcciones probadas en Consultas (PR #579); #576 derivó el `resource_metadata` de Consultas desde su URI de recurso (PR #582). El primer apply encontró el borde no verificado: APIM rechazó como path de API `.well-known/oauth-protected-resource`; se hizo el hotfix `a54ac6b`. La system key `mcp_extension` seguía obligando a desplegar #570 antes de aplicar #571, no bastaba con mergearlo.

**Ordenamos el resto del trabajo por oleadas.** Tras comprobar que el Container App de proyecciones no reconstruye desde cero sino que reanuda en `mt_event_progression`, refinamos #551 para renombrar solo el Container App a `ca-projections-asist-dev` (PR #580), sin tocar identidad ni environment. Para el MCP quedó el orden #575/#551, luego #571/#576, y después #572, #573 y #574. El glosario incorporó «Servidor MCP de Comandos» (PR #578).

## Problemas encontrados

**El scaffold generó más de lo que los issues anticipaban, pero no se había extralimitado.** Planificamos leyendo el agente de Mefisto 0.34.0; antes de ejecutar `/scaffold-mcp`, `.plugin-root` pasó a 0.35.0, cuyo agente también genera identidad, PRM, middleware, tests y settings OAuth. Reescribimos #570-#574 para fijar versión y responsabilidades reales. El texto informativo del skill seguía enumerando la salida anterior: lo reportamos al marco como harness#826. Los 12 tests generados pasaban por DLL directa, aunque `dotnet test --project` informaba cero tests también para el servidor hermano en esta máquina.

**La interfaz de APIM instalada no coincidía con la regenerada.** Ejecutar `/install-apim` sin reconciliación habría conservado el módulo antiguo y generado el archivo de Comandos contra la interfaz nueva. Además, el scaffold había reintroducido cuatro trampas pagadas por Consultas: orden de `<issuers>` y `<audiences>`, hostname regionalizado, backend sin rewrite y `data` en lugar de `resource` para listkeys. #575 conservó la mecánica verificada y abrió harness#827 como seguimiento. Quedó visible otro riesgo preexistente, sin issue aún: las Function Apps de dominio son `Anonymous` y aceptan `X-Tenant-Id` por hostname directo; un MCP de escritura vuelve más urgente restringir ese ingreso.

## Lo que descartamos

- Extraer ya una biblioteca de identidad compartida entre Consultas y Comandos: son dos apariciones; preferimos duplicar hasta un tercer servidor o un bug que afecte ambas copias (MEF-ADR-0018).
- Introducir `prm_backend_path` como parche específico de Comandos: el PRM compartido del módulo reconciliado eliminó esa necesidad. Tampoco agregamos `Mcp__PrmUri` a Consultas: abriría un ciclo Terraform entre gateway y Function App; #576 lo deriva de `Mcp__ResourceUri`.
- Hacer polling de la ficha tras un POST o forzar «hoy» para `fecha_inicio`: la proyección es asíncrona y el hecho persistido tiene fecha propia. Dejamos fuera del refactor el middleware 401 de Consultas, que hoy no se alcanza en las tool calls.
- Encadenar `deploy-projections.yml` por `workflow_run` dentro de #551: el workflow se autodispara al cambiar y una carrera con Infra CD se resuelve relanzándolo, sin ampliar el alcance del rename.

## Aprendizajes

1. **La versión del plugin es parte del contrato de un issue que depende de un scaffold.** Hay que resolver `.plugin-root` inmediatamente antes de redactarlo y fijar la versión; un cambio silencioso entre planificación y ejecución puede invalidar criterios de aceptación.
2. **Dos servidores MCP detrás de APIM requieren PRM y audiencias distinguibles, no dos APIs con la misma ruta.** RFC 9728 §3 permite publicar metadata asociada al recurso y usar la URL de `WWW-Authenticate`; un cliente que pida el recurso por defecto de Consultas no obtiene por ello acceso a Comandos.
3. **La validez de `terraform plan` no prueba que APIM acepte el path elegido.** El hotfix del punto inicial fue un rechazo del servicio durante el apply, no una incompatibilidad detectable por el plan.
