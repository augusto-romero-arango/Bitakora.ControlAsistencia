## Problemas encontrados

**La metadata de tenant que viajaba por Service Bus no tenía consumidor.** Al revisar #538 (fixtures de smoke declarando `ApplicationProperties["tenant-id"]`/`["user_id"]`), verificamos por decompilación (`ilspycmd`) que las claves eran las correctas para Wolverine 6.16.0 y Cosmos.MultiTenancy.CritterStack 2.3.0 — pero descubrimos que **en este proyecto nadie las lee**: ningún `Program.cs` monta un listener de Wolverine sobre Azure Service Bus; los eventos entran por `[ServiceBusTrigger]` de Azure Functions, cuya clase base deserializa solo el `Body` y descarta el `ServiceBusReceivedMessage` (y con él, sus `ApplicationProperties`). Consecuencia directa para el flip que arrancaba esa misma tarde: si los 4 dominios pasan a `AgregarTenantResolverHibrido()`, el camino `[ServiceBusTrigger]` no tiene `HttpContext`, cae al fallback `WolverineMessageContextTenantResolver`, y ese `IMessageContext` no viene de un envelope entrante — `TenantId` llega vacío y lanza. Declarar la metadata en el fixture no evita esto; el puente `ApplicationProperties` → `IMessageContext` simplemente no existe todavía. Quedó documentado como acción pendiente para `/install-auth` (o el issue que ejecute el flip), con tres opciones evaluadas, y como draft espejo en el marco (harness#798).

**Un bug de configuración menor, encontrado en el mismo review:** `configuration["Tenant:Id"] ?? PorDefecto` no caía al default cuando el valor era cadena vacía, y los appsettings de smoke usan `""` como convención de "sin configurar" (`ServiceBus:ConnectionString`, `Postgres:ConnectionString`). Con `Tenant:Id: ""` se mandaba un header vacío en vez del fallback — corregido con `string.IsNullOrWhiteSpace`.

**`coverage_classify_file` (del plugin) no reconoce los patrones del proyecto MCP.** Marcó 3 archivos como "sin clasificar" en el gate del PR #533: `*Tool.cs` (debería ser `logic` al 95%), `*Api.cs` en `/Infraestructura/` (debería ser `excluded`), y archivos con varios records DTO puros (la regla de exclusión exige exactamente 1 tipo por archivo). Ningún gap real de tests — la tool ya tenía cobertura unitaria en el mismo PR — pero ambos gaps quedaron como drafts al marco (harness#788, #789).

## Aprendizajes

1. **"El gate local no ejecuta smoke tests" es evidencia de que sí se pueden escribir sin key local, no de que deban omitirse.** La corrida real ocurre post-deploy en CI vía OIDC (MEF-ADR-0048 sección 4); confundir ambas lecturas es exactamente el gap que quedó documentado en harness#789.
2. **Verificar el productor de una clave de metadata (qué escribo) y verificar el consumidor (quién la lee en ESTE código, no en el que la librería supone) son dos gates distintos.** El segundo es el que decide si un cambio "forward-compatible" realmente lo es — el hallazgo de #538 pasó el primero y falló el segundo.
3. **El pin de `tools/list` en el nivel 3 (smoke e2e) es independiente del pin por reflexión del nivel 2** (`ComposicionDelServidorTests`): agregar una tool exige tocar ambos, no solo el que el pipeline TDD toca por defecto.
4. **Antes de crear un draft de mejora al harness, vale la pena buscar en los issues existentes.** Evitó duplicar harness#789 dos veces en la misma semana.
5. **Un `ScheduleWakeup` que empaqueta una acción de alto impacto (parar/arrancar una base de datos en producción-like) debe ser bloqueado por el clasificador de permisos**, incluso cuando el protocolo en sí está autorizado — la ejecución correcta es en el turno activo, supervisada con `Bash` directo y `Monitor` acotado, no delegada a un wakeup autónomo.
